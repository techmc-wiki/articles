本篇是[连续的方块更新及其分析方法](./连续的方块更新及其分析方法.zh.md)的进阶补充，讨论 1.19 起 Java 版引入的**更新器**（`NeighborUpdater`）如何真正传递NC更新与PP更新，以及它与旧版“调用即执行”的更新链在什么情况下会给出不同的结果。

**主要内容**

- 旧版本：调用即执行的更新链
- 1.19+：先登记、后执行的更新器
- 新旧结果何时不同：含水活板门与计划刻顺序反转
- 更新组、更新跳略与因果追溯
- 源码分析

> [!IMPORTANT]
> 先说结论：对于绝大多数红石分析，上一篇给出的深度优先分析方法**依然正确**。只有当一个方块在**发出更新之后**还要做别的事情（添加计划刻、再次修改方块……）时，新旧版本才会出现差别。

## 旧版本：调用即执行

在 1.18.2 及更早的版本中，“发出更新”就是**直接调用**邻居的响应函数：方块A发出NC更新时，游戏立刻调用方块B响应NC更新的函数；B在其中改变状态并发出更新，游戏又立刻调用C的响应函数……整条更新链由 Java 自身的调用栈承载（参见[附录-栈](../Appendix/栈.zh.md)），调用栈的嵌套关系就是更新之间的因果关系。

以PP更新为例，1.18.2 中`setBlock`发出PP更新时直接遍历邻居并调用它们的`updateShape`：

```java mc=1.18.2 mapping=mojmap
for (Direction direction : BlockBehaviour.UPDATE_SHAPE_ORDER) {
    mutableBlockPos.setWithOffset(pos, direction);
    BlockState neighbor = level.getBlockState(mutableBlockPos);
    BlockState updated = neighbor.updateShape(
        direction.getOpposite(), this.asState(), level, mutableBlockPos, pos
    );
    Block.updateOrDestroy(neighbor, updated, level, mutableBlockPos, flag, recursionLeft);
}
```

套用上一篇的矿洞比喻：你每走到一格就插下火把，然后**立刻**按西东下上北南的顺序钻进下一条岔路，直到无路可走才回头。如果你在这一格本来还有别的事要做——比如在墙上画个记号——那么这件事只能等你把所有岔路都探索完、走回这一格之后再做。

这种实现有一个先天问题：更新链有多长，Java 调用栈就有多深。足够长的更新链会耗尽调用栈，抛出`StackOverflowError`，轻则使后续更新被跳过（这正是早期更新抑制器的原理），重则直接使服务端崩溃[^1]。

[^1]: 例如 [MC-231185](https://mojira.dev/MC-231185)：以铁轨为预设的超平坦世界在加载时因`StackOverflowError`崩溃。该问题在 [22w11a](https://minecraft.wiki/w/Java_Edition_22w11a) 中修复，同一快照加入了限制连锁更新数量的`max-chained-neighbor-updates`服务器属性。

## 1.19+：先登记，后执行

从 1.19（快照 22w11a）起，每个世界持有一个**更新器**（`ChainRestrictedNeighborUpdater`）。NC更新与PP更新都不再直接调用邻居，而是先被打包成一个**更新项**（Entry）交给更新器，由更新器决定何时执行。

| 更新项                  | 由什么方法产生                                                                     | 执行一次做什么                                       |
| ----------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `SixWayEntry`           | `updateNeighborsAlways`、`updateNeighborsExcept`（`setBlockState`的NC更新也走这里） | 按西东下上北南的顺序，向**一个**方向发出NC更新        |
| `SimpleEntry`           | `updateNeighbor(pos, sourceBlock, sourcePos)`                                      | 对一个方块发出NC更新                                 |
| `StatefulEntry`         | `updateNeighbor(state, pos, ...)`，如比较器更新、铁轨对自身的更新                  | 对一个方块发出NC更新，但使用**登记时**记录的方块状态 |
| `StateReplacementEntry` | `replaceWithStateForNeighborUpdate`，即PP更新                                      | 对一个方块发出PP更新                                 |

注意`SixWayEntry`的“六个方向”是分六次执行的，每执行一次只更新一个方向。这一点对下文的执行顺序至关重要。

更新器的行为可以概括为两条规则：

**规则一：更新器空闲时，登记即执行。** 如果更新器当前没有在工作，新登记的更新项会立刻被执行，并且更新器会一直工作，直到这一更新项引发的**全部**连锁更新都执行完毕，才把控制权交还给发出更新的代码。从发出者的角度看，这与旧版的“调用即执行”没有区别。

**规则二：更新器工作时，只登记不执行。** 如果更新器正在执行某个更新项，那么在此期间新发出的更新只会被记入一个“待办”列表。等当前这一步执行完毕（即某个方块的响应函数**整个返回**之后），更新器才按**登记的先后顺序**依次处理待办：每一项都会连同它引发的全部连锁更新一起执行完毕，才轮到下一项；所有待办处理完毕后，再回到之前被打断的更新项（比如一个只执行了一部分方向的`SixWayEntry`）继续执行。

回到矿洞：现在你到达一格后，会先把这一格的**所有事情**做完——插火把、画记号——同时把要钻的岔路**记在本子上**；这一格的事情全部做完之后，你才按本子上的顺序逐一钻进去。在每一条岔路里，你也遵守同样的规矩。

### 为什么旧的分析方法依然成立

规则二只改变了一件事：**方块的响应函数在返回之前，看不到自己发出的更新所造成的任何后果。** 而子更新之间的先后顺序（按登记顺序、每一项都“深入到底”再处理下一项）与旧版的深度优先完全一致。

所以，如果一个方块只是“改变状态，发出更新，然后什么都不做”，那么新旧版本的结果完全相同。以上一篇中的BUD铁轨链为例，动力铁轨在响应NC更新时的行为是：

```java
world.setBlockState(pos, state.with(POWERED, bl2), Block.NOTIFY_ALL);
world.updateNeighborsAlways(pos.down(), this);
if (state.get(SHAPE).isAscending()) {
    world.updateNeighborsAlways(pos.up(), this);
}
```

它依次登记：自身的NC更新、自身六个方向的PP更新、以下方方块为更新核的NC更新（斜放时再加上以上方方块为更新核的NC更新）。这与旧版中“先NC、后PP、再更新下方”的调用顺序一一对应，因此上一篇得出的NC/PP更新顺序在 1.20.1 中保持不变。

### 哪里是“顶层”

规则一与规则二的分界在于：发出更新时，更新器是否正在工作。

| 场合                                                                                                   | 更新器状态 | 发出的更新                           |
| ------------------------------------------------------------------------------------------------------ | ---------- | ------------------------------------ |
| 玩家交互（右键、放置、破坏）、计划刻执行、方块事件执行、方块实体运算（如活塞到位）、随机刻、实体行为等 | 空闲       | 立刻执行完整条连锁，与旧版相同       |
| 方块响应NC更新（`neighborUpdate`）、响应PP更新（`getStateForNeighborUpdate`），以及其中触发的`onBlockAdded`、`onStateReplaced`等 | 工作中     | 只登记，待当前响应函数返回后再执行   |

也就是说，**新旧差异只出现在“方块对更新做出响应”的过程中**。一个中继器在计划刻中亮起时发出的更新会像旧版一样立刻执行；而一个被NC更新激活的活板门发出的PP更新，则要等活板门的响应函数返回后才会执行。

## 新旧结果何时不同

当一个方块的响应函数在**发出更新之后**还做了别的事时：

- 旧版中，这些事发生在它发出的更新所引发的**整条子链结束之后**；
- 新版中，这些事发生在**整条子链开始之前**。

### 实例：含水活板门

活板门响应NC更新的代码如下：

```java
public void neighborUpdate(BlockState state, World world, BlockPos pos, Block sourceBlock, BlockPos sourcePos, boolean notify) {
    if (!world.isClient) {
        boolean bl = world.isReceivingRedstonePower(pos);
        if (bl != state.get(POWERED)) {
            if (state.get(OPEN) != bl) {
                state = state.with(OPEN, bl);
                this.playToggleSound(null, world, pos, bl);
            }

            world.setBlockState(pos, state.with(POWERED, bl), Block.NOTIFY_LISTENERS);
            if (state.get(WATERLOGGED)) {
                world.scheduleFluidTick(pos, Fluids.WATER, Fluids.WATER.getTickRate(world));
            }
        }
    }
}
```

活板门先以`FLAG=2`调用`setBlockState`（只发出PP更新），**然后**为自身的水添加计划刻。

设一个含水活板门T被红石信号激活，T的东侧紧邻一个水源W（W不与信号源相邻），且两者此前都没有待执行的流体计划刻。水源在受到PP更新时会为自己添加计划刻（`FluidBlock.getStateForNeighborUpdate`）。

**1.18.2：**

```plaintext
├── T 受到NC更新
│   ├── T 改变状态，发出PP更新
│   │   ├── ...
│   │   ├── W 受到PP更新
│   │   │   └── W 添加流体计划刻 ①
│   │   └── ...
│   │   * T PP更新完成 *
│   └── T 为自身的水添加流体计划刻 ②
```

**1.20.1：**

```plaintext
├── T 受到NC更新
│   ├── T 改变状态，PP更新被登记（尚未执行）
│   └── T 为自身的水添加流体计划刻 ①
│   * T 的响应函数返回 *
└── 更新器处理待办：T 的PP更新
    ├── ...
    ├── W 受到PP更新
    │   └── W 添加流体计划刻 ②
    └── ...
```

两个流体计划刻都是水（延迟均为`5gt`）、优先级都是默认的`0`，执行时间和优先级都相同，于是执行顺序完全由**子顺序**`subTickOrder`即添加的先后决定（参见[计划刻与计划刻元件](../MicroTiming/计划刻与计划刻元件.zh.md)）。旧版中W的水先流动，新版中T的水先流动——**两股水的计划刻顺序反转了**。

对依赖两股水先后流动的机器而言，这一反转会直接改变机器的行为。

### 同一个装置，两种触发方式

活板门被玩家右键时调用的是另一段代码：

```java
public ActionResult onUse(BlockState state, World world, BlockPos pos, PlayerEntity player, Hand hand, BlockHitResult hit) {
    ...

    world.setBlockState(pos, state, Block.NOTIFY_LISTENERS);
```

两段代码的结构完全相同，但玩家交互发生在**顶层**：此时更新器空闲，`setBlockState`发出的PP更新会立刻执行完毕。读者不妨先自己推断：玩家右键打开上例中的活板门T时，T和W的流体计划刻谁先添加？

答案：:hidden[W 先添加，T 后添加，与 1.18.2 的结果相同。也就是说，在 1.20.1 中，同一个含水活板门“用手开”和“用红石开”时，两股水的计划刻顺序相反。]

### 其他值得留意的情形

- **一次响应中多次修改世界。** 如果一个方块在响应函数里先后两次修改世界，那么第二次修改会发生在第一次修改所引发的连锁更新**之前**。于是第一次修改的连锁更新“看到”的，已经是被第二次修改过的世界。
- **登记时记录的状态。** PP更新项记录的是发出更新那一刻的方块状态`neighborState`；`StatefulEntry`记录的是被更新方块在登记时的状态。如果在执行前这些方块又发生了变化，响应方拿到的会是过时的状态。

## 更新组与更新跳略

更新器从空闲开始工作、到所有待办处理完毕重新空闲为止，这一次执行的全部更新项称为一个**更新组**。

更新器内部的`depth`字段名为“深度”，实际上是一个**计数器**：更新组内每登记一个更新项就加一，直到整个更新组结束才清零。当计数达到上限`max-chained-neighbor-updates`（默认`1000000`）后，此后登记的更新项会被直接丢弃，游戏只在第一次丢弃时输出一条日志：

```plaintext
Too many chained neighbor updates. Skipping the rest. First skipped position: ...
```

已经登记的更新项仍会正常执行。利用这一机制使某些更新被跳过，称为[更新跳略](https://zh.minecraft.wiki/w/Tutorial:更新跳略)（Update Skipping）。需要注意：

- 计数的单位是**更新项**而不是“被更新的方块”，一个`SixWayEntry`只计一次。
- 上限只能在专用服务器的`server.properties`中修改，设为负数时不再限制；单人游戏的内置服务器固定为`1000000`。
- 更新链的长度不再消耗 Java 调用栈，长更新链本身不会再导致`StackOverflowError`。
- PP更新原有的`512`层深度限制（`setBlockState`的`maxUpdateDepth`参数）仍然存在，与更新组的计数相互独立。
- 若更新组执行过程中抛出异常，更新器会清空**整个更新组**中尚未执行的全部更新项，而不仅仅是当前分支。关于利用异常中断更新的方法，参见[更新抑制](https://zh.minecraft.wiki/w/Tutorial:更新抑制)。

## 因果关系变得难以追溯

在旧版中，调用栈本身就是因果链：任意时刻暂停游戏，或者查看崩溃报告，都能看到`A → B → C`的完整调用路径。

在新版中，更新项只记录目标坐标、发出更新的方块与坐标等信息，**不记录自己是由哪个更新项派生出来的**；执行时调用栈里也只剩下当前这一项。调试器和崩溃报告都只能告诉你“正在更新谁”，不能告诉你“为什么会更新它”。

对于分析而言，需要把“方块B因为受到更新而改变”理解为两个分离的时刻：

1. B的响应函数执行，B改变状态，B的更新被**登记**；
2. B的响应函数返回之后，B的更新才被**执行**。

把这两个时刻混为一谈，就会在上文含水活板门这样的情形中得出错误的结论。

## 源码分析

### 更新器的创建与接入

每个`World`在构造时创建自己的更新器：

```java file=net/minecraft/world/World.java lines=149
this.neighborUpdater = new ChainRestrictedNeighborUpdater(this, maxChainedNeighborUpdates);
```

服务端世界把所有NC更新方法都转交给更新器：

```java file=net/minecraft/server/world/ServerWorld.java lines=1127-1145
@Override
public void updateNeighborsAlways(BlockPos pos, Block sourceBlock) {
    this.neighborUpdater.updateNeighbors(pos, sourceBlock, null);
}

@Override
public void updateNeighborsExcept(BlockPos pos, Block sourceBlock, Direction direction) {
    this.neighborUpdater.updateNeighbors(pos, sourceBlock, direction);
}

@Override
public void updateNeighbor(BlockPos pos, Block sourceBlock, BlockPos sourcePos) {
    this.neighborUpdater.updateNeighbor(pos, sourceBlock, sourcePos);
}

@Override
public void updateNeighbor(BlockState state, BlockPos pos, Block sourceBlock, BlockPos sourcePos, boolean notify) {
    this.neighborUpdater.updateNeighbor(state, pos, sourceBlock, sourcePos, notify);
}
```

PP更新同理。`AbstractBlockState.updateNeighbors`对每个方向调用`world.replaceWithStateForNeighborUpdate`，而`World`覆写了该方法：

```java file=net/minecraft/world/World.java lines=368-373
@Override
public void replaceWithStateForNeighborUpdate(
    Direction direction, BlockState neighborState, BlockPos pos, BlockPos neighborPos, int flags, int maxUpdateDepth
) {
    this.neighborUpdater.replaceWithStateForNeighborUpdate(direction, neighborState, pos, neighborPos, flags, maxUpdateDepth);
}
```

[更新的概念与不同类型的更新](./更新的概念与不同类型的更新.zh.md)中展示的`WorldAccess.replaceWithStateForNeighborUpdate`是接口的默认实现，会直接同步执行PP更新；对于游戏中的`World`，它被上面的覆写取代[^2]。

[^2]: 世界生成阶段使用的`ChunkRegion`没有覆写该方法，因此其中的PP更新仍是同步递归执行的。这不影响正常游戏中的红石分析。

### 登记：`enqueue`

`ChainRestrictedNeighborUpdater`维护三个状态：一个作为栈使用的`ArrayDeque queue`，一个待办列表`List pending`，以及计数器`depth`。所有更新项都经由`enqueue`登记：

```java file=net/minecraft/world/block/ChainRestrictedNeighborUpdater.java lines=55-72
private void enqueue(BlockPos pos, ChainRestrictedNeighborUpdater.Entry entry) {
    boolean bl = this.depth > 0; // 更新器是否正在工作
    boolean bl2 = this.maxChainDepth >= 0 && this.depth >= this.maxChainDepth; // 是否已达到上限
    this.depth++;
    if (!bl2) {
        if (bl) {
            this.pending.add(entry); // 规则二：只登记到待办
        } else {
            this.queue.push(entry); // 规则一：压入栈
        }
    } else if (this.depth - 1 == this.maxChainDepth) {
        LOGGER.error("Too many chained neighbor updates. Skipping the rest. First skipped position: " + pos.toShortString());
    }

    if (!bl) {
        this.runQueuedUpdates(); // 规则一：立刻开始执行，直到整个更新组结束
    }
}
```

`depth`只增不减，直到`runQueuedUpdates`结束时才在`finally`中清零，因此它统计的是整个更新组登记过的更新项总数，而不是嵌套深度。

### 执行：`runQueuedUpdates`

```java file=net/minecraft/world/block/ChainRestrictedNeighborUpdater.java lines=74-96
private void runQueuedUpdates() {
    try {
        while (!this.queue.isEmpty() || !this.pending.isEmpty()) {
            // 把待办倒序压栈，使最早登记的一项位于栈顶
            for (int i = this.pending.size() - 1; i >= 0; i--) {
                this.queue.push(this.pending.get(i));
            }

            this.pending.clear();
            ChainRestrictedNeighborUpdater.Entry entry = this.queue.peek();

            // 反复执行栈顶项的“一步”，直到它产生了新的待办，或它已全部执行完毕
            while (this.pending.isEmpty()) {
                if (!entry.update(this.world)) {
                    this.queue.pop();
                    break;
                }
            }
        }
    } finally {
        this.queue.clear();
        this.pending.clear();
        this.depth = 0;
    }
}
```

`Entry.update`返回`true`表示这一项还有后续步骤，返回`false`表示已执行完毕。两层循环合起来实现了前文的规则二：

1. 执行栈顶项的一步。这一步就是一次完整的方块响应函数调用，其中发出的所有更新都进入`pending`。
2. 若这一步没有产生待办且该项还有后续步骤，继续执行下一步（如`SixWayEntry`的下一个方向）。
3. 一旦产生了待办，立即停下：把待办**倒序**压栈，使它们按登记顺序依次位于栈顶，然后从最早登记的那一项开始执行。被打断的项留在栈中，等上方的待办全部出栈后再继续。

这正是用一个显式的栈模拟了旧版的递归调用：“栈顶优先”保证了深度优先，“倒序压栈”保证了同一次响应中登记的兄弟更新项按登记顺序执行。唯一的区别在于，模拟的粒度是“一次完整的响应函数调用”，而不是“一次更新方法调用”。

`finally`块保证了无论更新组是正常结束还是因异常中断，栈、待办和计数器都会被清空。

### 六向NC更新：`SixWayEntry`

```java file=net/minecraft/world/block/ChainRestrictedNeighborUpdater.java lines=127-137
@Override
public boolean update(World world) {
    BlockPos blockPos = this.pos.offset(NeighborUpdater.UPDATE_ORDER[this.currentDirectionIndex++]);
    BlockState blockState = world.getBlockState(blockPos);
    blockState.neighborUpdate(world, blockPos, this.sourceBlock, this.pos, false);
    if (this.currentDirectionIndex < NeighborUpdater.UPDATE_ORDER.length && NeighborUpdater.UPDATE_ORDER[this.currentDirectionIndex] == this.except) {
        this.currentDirectionIndex++;
    }

    return this.currentDirectionIndex < NeighborUpdater.UPDATE_ORDER.length;
}
```

每次只更新一个方向，用`currentDirectionIndex`记住进度，并跳过`except`方向。因为它是一个有状态的对象而非一次性调用，所以在某个方向上被子更新打断后，可以在栈中等待，稍后从下一个方向继续。

### 含水活板门的栈追踪

以含水活板门为例，设T被`SixWayEntry S`的某个方向更新到。用`PP(T→X)`表示T对X方向邻居的PP更新项：

| 步骤                         | 发生的事情                                                        | 执行后的栈（左为栈顶）                           | 待办                 |
| ---------------------------- | ----------------------------------------------------------------- | ------------------------------------------------ | -------------------- |
| 执行`S`的一步                | T改变状态并登记6个PP更新项；T为自身的水添加计划刻 ①               | `S`                                              | `PP(T→西)`…`PP(T→上)` |
| 倒序压栈                     |                                                                   | `PP(T→西)` `PP(T→东)` … `PP(T→上)` `S`            | 空                   |
| 执行`PP(T→西)`并出栈         | 西侧邻居响应PP更新                                                | `PP(T→东)` … `S`                                 | 空                   |
| 执行`PP(T→东)`并出栈         | W响应PP更新，添加计划刻 ②                                         | `PP(T→北)` … `S`                                 | 空                   |
| ……                           |                                                                   |                                                  |                      |
| 继续执行`S`的剩余方向        |                                                                   | `S`                                              | 空                   |

PP更新的方向顺序为西东北南下上，因此东侧的W在第二个被执行。可以看到，T的响应函数（含计划刻 ①）在第一步中就已全部完成，而W的计划刻 ② 要等到待办被处理时才添加。

## 练习

1. 在上一篇的BUD铁轨链中，若某根动力铁轨在响应NC更新时**先**以自身为更新核发出NC更新、**再**改变自身状态，那么与旧版相比，它下游的铁轨在受到更新时看到的这根铁轨状态有何不同？

   答案：:hidden[旧版中，下游铁轨受到更新时这根铁轨尚未改变状态；1.20.1 中，NC更新被登记后要等这根铁轨的响应函数返回才执行，此时它已经改变了状态。顺序“先发更新、后改状态”在新版中实际上等价于“先改状态、后发更新”。]

2. 一个计划刻元件在执行计划刻时，先以`FLAG=2`改变状态，再添加下一次计划刻。它发出的PP更新所引发的计划刻，与它自己的下一次计划刻，哪一个的子顺序更小？新旧版本是否一致？

   答案：:hidden[PP更新引发的计划刻子顺序更小，新旧版本一致。计划刻执行发生在顶层，更新器空闲，PP更新会在 setBlockState 内立刻执行完毕。]
